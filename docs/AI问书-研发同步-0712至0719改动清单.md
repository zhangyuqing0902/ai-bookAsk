## 一、数据契约变更（P0 · 后端优先看）

### 1.1 KP 状态枚举扩容 —— 破坏性变更

| | 取值 |
|---|---|
| **原先** | `draft` / `published` / `archived` |
| **之后** | `draft` / `published` / `unlisted` / `deleted` |

逐值对照：

| 原值 | 现值 | 语义 |
|---|---|---|
| `draft` | `draft` | 草稿，未上架，前台不可见 |
| `published` | `published` | 已发布，正常售卖与访问 |
| `archived` | **废弃，并入 `deleted`** | 原「归档」态取消，**历史数据需迁移** |
| — | **`unlisted`（新增）** | 已下架：停止新售，**已解锁权益保留**，前台标「已下架」并拦截，可重新发布 |
| — | **`deleted`（新增）** | 已删除：**逻辑删除**，三端不展示，数据库保留全部数据 |

状态机：

```
draft ──发布──> published ──下架──> unlisted ──重新发布──> published
                   │                  │
                   └────── 删除 ───────┴──> deleted（终态，软删，界面不可恢复）
```

**为什么改**：原四态里「归档」与「删除」在运营心智里区分不出来，运营问「归档和删除有什么区别」答不上来 → 合并为三态 + 一个终态。「下架」独立出来承载「临时禁访问、之后还要再上」的真实运营场景。

**后端动作**：枚举扩容；`archived` 存量数据迁移为 `deleted`；**不要实现物理删除分支**。

> 📌 代码内有一处**注释与实现矛盾**，以实现为准：`packages/mock/src/types.ts:41` 的注释仍写「无业务关系时物理移除」，但 `packages/mock/src/rules.ts:146-149` 明确「不存在物理删除」。注释是上一版遗留，已列入待修。

### 1.3 新增业务规则层 `packages/mock/src/rules.ts`

远端不存在此文件。把原先散在各页面里的业务规则集中定义，共 30 个导出。后端实现时**以这个文件为准**，关键几条：

| 函数 | 返回 | 业务含义 |

## 二、业务规则反转（P1 · 与旧文档结论相反，重点确认）

这一节的每一条，**结论都和你们手上的 PRD v1.3 相反**。请优先对齐。

### 2.1 删除：物理删除 → 逻辑删除

- **原先**：删除连带清除知识库文件、向量、二维码、分享，**不可恢复**
- **之后**：**全平台一律逻辑删除**。三端界面不可见，数据库保留全部数据（订单/权益/文件/向量/二维码/分享记录）；C 端历史凭证保留并统一标「已失效」
- **界面文案禁用**「物理删除 / 彻底删除 / 永久删除」
- **为什么**：删除后用户来投诉「我买的东西没了」时，客服要能查到记录、能解释、能退款。物理删除让售后无法追溯。

### 2.2 下架：买断放行 → 一律拦截

- **原先**（0716 结论）：已买断永享的内容，即使 KP 下架也应放行，因为「买断是契约」
- **之后**（0717 拍板推翻）：**下架＝运营临时禁访问**，「我的纸书」「我的永享」对已下架 KP **一律拦截**并标「已下架」；已解锁的则双标并列
- **权益不清除**，重新上架自动恢复
- **为什么**：下架的真实场景是「内容有问题、先撤下来改」。如果买断用户还能看，等于问题内容还在对外服务。权益保留 + 重新上架自动恢复，已经足够保护用户利益。
- ⚠️ **这是一次产品口径反转**：已付费买断的用户，在 KP 下架期间也看不了。

### 2.3 订单：支付成功才落库

- **原先**：下单即落库，有「待支付」态
- **之后**：**支付回调成功才写订单**，中断不生成订单。C 端订单态收敛为 已支付 / 已核销 / 退款售后，**没有「待支付」**，也不需要「去支付」入口
- **为什么**：待支付订单在实际业务里 99% 是垃圾数据，占着订单号还要写清理逻辑。

### 2.4 KP 状态命名两后台统一

- **原先**：机构后台用「未发 / 已发」，平台后台用「草稿 / 已发布 / 已下架」
- **之后**：统一为 **草稿 / 已发布 / 已下架**。按钮：草稿→发布、已发布→下架、已下架→重新发布
- **为什么**：同一个东西两个后台两套叫法，跨端沟通成本高。
- **测试注意**：所有「未发 / 已发」字样的用例要全量替换；且**同一时刻只有一个状态按钮**（不是原来固定两枚），按文案定位元素的脚本要改。

### 2.5 停用父机构不级联

- **原先**：文案暗示停用会影响下级
- **之后**：**停用父机构仅暂停该机构自身服务，不自动停用子机构**；如需批量停用必须逐家确认
- **为什么**：父子机构是出版集团与分社的关系，分社有独立经营主体，不能因为集团欠费就把分社停了。

### 2.6 订阅删除护栏放宽

- **原先**：非已过期 **且** KP/存储/Token 用量全为 0 **且** 无加油包，四条全满足才能删
- **之后**：**未生效 / 已生效都能删，只有「已过期」不可删**。已产生用量的会弹红色强警条并列出具体用量数值；并明示「**删除 ≠ 退款**」
- **为什么**：真实场景是商务「建错了」需要撤销，原护栏太严导致建错就永远删不掉。
- ⚠️ **本批风险最高的行为变更**，回归重点：删除生效中订阅后机构配额与当前生效订阅卡的表现。

### 2.7 微信「回调域名」→「回调地址」

- **原先**：字段名「网页授权回调域名」，说明「不含 http:// 与路径」
- **之后**：改「回调地址」，「须与微信后台配置完全一致，**并包含协议与实际回调路径**」
- **为什么**：微信开放平台实际校验的是完整 URL，原字段定义会导致配置怎么填都不对。
- **后端动作**：字段校验规则要跟着从「域名」改为「完整 URL」。

## 三、移动端 H5（apps/mobile-h5）

### 3.1 新增统一判活入口 `/kp/:kpId` 【新增页面】

`apps/mobile-h5/src/screens/KpGate.tsx`（全新）

- **原先**：无此路由。扫码/前台直达没有统一入口，不做任何 KP 状态校验，任何 KP 都能进会话
- **之后**：所有前台入口（前台地址 + 扫码）统一走 `/kp/:kpId` 判活，三态分流：

| 状态 | 判定 | 提示 |
|---|---|---|
| 正常 | `published` | 进会话 |
| 已下架 | `unlisted` | 「已下架，若有问题请联系客服」 |
| 已失效 | `deleted` / `draft` / **id 不存在** | 「已失效，若有问题请联系客服」 |

- 失效后停留 3 秒 → 跳转**同机构最新已发布 KP** 的全新会话；未登录先跳登录；该机构无已发布 KP 则不跳转、停留本页
- **接口要求**：① 按 kpId 返回 `status` 与 `orgId`；**软删的 KP 不能返 404**，要能查到 `status='deleted'` 才能区分「已失效」和其他错误。② 需要「按 orgId 取最新已发布 KP」的查询能力
- **为什么**：原先没有统一判活，用户扫到一个已下架的码会直接进会话然后发现内容缺失，体验断裂。

### 3.2 我的纸书 / 我的永享：两级拦截

- **原先**：所有卡片一律可点，直接进会话，无状态判断
- **之后**：`unlisted` → 「该内容已下架」；`deleted` → 「该内容已失效」，均拦截不进会话
- 拦截**不区分是否已解锁**（见 2.2）
- 视觉：整卡降透明度；「已下架/已失效」灰标挂在扫码时间后；「已解锁」皇冠角标保留在卡片层并同步变淡 → **一张「已下架且已解锁」的卡会同时出现两个标**
- 提示语**不带 KP 名**（「该内容已下架…」而非「《XX》已下架…」）

### 3.3 会员开通页：改为「购买方式即续费语义」双模式

- **原先**：两档＝「首月特惠 ¥9.9」/「月度 ¥19.9」，续费规则藏在小字里
- **之后**：两档＝**连续包月** / **单月会员**，续费语义提到卡名旁的 pill：

| 档位 | 角标 | 续费语义 pill | 价格 |
|---|---|---|---|
| 连续包月 | 首月特惠 | 自动续费 · 可随时取消 | ¥9.9 首月，次月起 ¥19.9/月 |
| 单月会员 | — | 一次性购买 · 不自动续费 | ¥19.9 / 1 个月，到期失效 |

- 协议改为**真实交互**：**默认未勾选**（0719 合规修订，含《自动续费协议》的场景不做默认代勾），未勾选点按钮 → 拦截并 toast；《自动续费协议》**仅连续包月**显示
- 按钮文案随档位变化（「¥9.9 开通连续包月」/「¥19.9 购买单月会员」）
- **价格本身没变**，变的是续费语义的表达位置
- **为什么**：原「月度 + 按月自动续费」的说法，用户分不清「这次付的钱买了多久、下个月还扣不扣」，客服咨询量集中在这里。改成「买法即续费法」后不言自明。
- **接口要求**：需区分「连续包月（签约代扣）」与「单月（一次性）」两种商品，不是一个价格字段
- ⚠️ 已知未完成：协议链接目前是空实现，未跳 `/agreement/:type`

### 3.4 订单：双维度筛选 + 退款记录

- **原先**：只有一行类型 Tab（全部/会员/永享/兑换码）
- **之后**：类型 Tab + **状态 chips**（全部 / 已支付 / 退款售后）双维度；`部分退款|全额退款|退款中` 归并为「退款售后」；**兑换码 Tab 隐藏状态 chips**（能展示的兑换码必为已核销）
- 订单卡片新增退款条，**逐笔全量展示不截断**
- 订单详情新增「退款记录」卡片，底部固定政策说明：「全额退款仅撤销由该订单单独产生的权益」「部分退款及其他独立赠送、兑换权益不受影响」

### 3.5 兑换码：新增三类失败拦截

- **原先**：有输入就 toast「兑换成功」，**没有任何失败态**
- **之后**：弹窗形式的三类失败——**未到生效时间**（含具体生效时间）/ **已过期** / **机构已停用**
- **接口要求**：兑换接口需返回可区分的失败码
- ⚠️ 演示码提示文案（FUTURE/EXPIRED/STOPPED）上线前需移除

### 3.6 会话页：失效媒体不再弹付费墙

- **原先**：媒体只分「已锁→弹付费墙」「未锁→进预览」
- **之后**：新增前置判断——关联 KP 失效时，即使 `locked=true` 也**不弹付费墙**，只 toast
- **为什么**：避免用户为看不了的内容付款

### 3.7 其他

- **开发端口 5173 → 5170**（5173 被其他常驻项目占用）。CI、联调文档、自动化脚本需同步
- 协议页：「到期前 72 小时宽限期」→「**到期赠 72 小时会员缓冲使用期**」（语义从到期前提醒变为到期后延长）
- 权益口径写进协议：「纸书扫码解锁对应 KP **当前及未来新增的全部内容**并永久保留」

### 4.3 共享 KP 只读（实时同步导入）

- **之后**：`importMode='realtime'` 触发只读——隐藏二维码/分享 Tab、隐藏状态操作、表单禁用、**知识库数据可正常读，仅操作按钮置灰并 toast「无权限操作」**、仅「复制前台访问地址」可用
- ⚠️ **只读是操作级不是数据级**——数据可读可查是预期行为，不是漏做权限。这是本轮最容易测错的点
- 平台超管侧传 `consumerReadonly={false}`，保留监管操作（与机构后台行为不同，有意为之）

### 4.4 数据看板：留存率按注册批次重构

- **原先**：留存率是三个写死的百分比，**跟着观察区间联动**——口径本身是错的
- **之后**：按**注册批次 cohort** 重构，三张等宽卡（D+1 / D+7 / D+30），每节点独立 `rate / sample / cutoff / status / readyDate`
  - 未成熟节点显示「**尚未到统计时间**」+ 预计可统计日期，**不显示 0% 或空条**
  - 同一注册日的三个节点**共用同一样本**（分母相同）
  - 独立的「注册批次」筛选，与页面区间筛选**互不影响**
- **为什么**：留存必须按「哪天注册的人、第 N 天回没回来」算。按观察区间算出来的数字没有业务含义。
- ⚠️ **留存段与区间筛选互不影响是设计，不是联动 bug**
- **接口要求**：留存接口需返回 `rate/sample/cutoff/status/readyDate` 五要素

### 4.5 数据看板：日活/周活/月活口径修订

- **原先**：DAU/WAU/MAU 是**固定窗口快照硬编码**，tooltip 明写「不随时间区间变化」
- **之后**：移入用户分析 Tab，**随区间联动并环比**（区间内日均去重口径）
- ⚠️ **已知不一致（待修）**：导出 Sheet 里仍标注「实时快照，不随区间联动」，与页面口径矛盾

### 4.6 导出体系 spec 化

- **原先**：6 处导出按钮全是 `toast('导出整页')` **空壳**；唯一真导出是答案反馈的 `.txt`
- **之后**：统一产真 xlsx。命名规范 `AI问书_{机构名|全域}_{业务名}数据导出.xlsx`；**导出上限 10000 条**，超限弹窗拦截不下载
- 页面导出按钮与文档模板样张**同源**，不会出现「文档说有这列、实际导出没有」
- 导出会把**当前筛选条件写进文件表头第 3 行**

### 4.7 系统配置：会员价格改三档

- **原先**：两个价格字段（首月折扣价 / 月度价）
- **之后**：**三个价格字段**——连续包月的「首月价格」+「次月起价格」，单月的「单月价格」，与前台两档卡一一对应
- 保存价格、切换回答策略均加二次确认

### 4.8 其他

- 订单三个时间筛选从**纯装饰**改为真过滤（原先无 onChange）

- C 端用户列表新增「注册时间」列

- ⚠️ 已知不一致：答案反馈的时间筛选目前只影响导出的筛选条件回显，**不过滤列表**（与订单页行为不一致，需产品确认是否为 bug）

## 七、给测试同学的高风险点

1. **清 localStorage**：`aba-org-kp-lifecycle`（KP 状态）、`aba-platform-org-tree`（机构层级）会跨轮次污染结果
2. **KP 状态按钮是互斥单枚**，不是固定两枚；按文案定位的脚本要全改
3. **删除语义反转**：从「不可恢复清除」变「逻辑删除、数据库保留、界面不展示」——「删除后能否找回」的预期是「界面找不回、数据保留」
4. **下架语义反转**：已买断永享的内容在下架期间**也不可访问**
5. **实时同步只读是操作级**：数据可读可查是预期，不是漏做权限
6. **留存段与区间筛选互不影响**是设计，不是 bug；未成熟节点显示「尚未到统计时间」不是显示异常
7. **导出超限**：唯一入口是「全域用户 → 不加筛选 → 导出」
8. **订单兑换时间筛选**一旦启用，无兑换时间的订单会被排除（含全部非兑换码订单）
9. **环比标签含真实日期区间**，依赖系统时间 → 截图基线类回归会持续 diff
10. **端口改为 5170**（移动端）
