## 一、原型改动

### 1. 机构后台 · 知识 KP 列表：分享方不再显示分享标识

- 「心血管分册 · 第4版」等分享方 KP 移除「实时分享 · 分享方」标签。
- 分享标识只保留在**接收方**：「分享导入 · 实时」「分享导入 · 快照」。
- 分享方视角下该 KP 与自建 KP 展示一致。

### 2. 平台后台 · 机构详情 · 微信配置：新增两个文件上传入口

| 位置 | 新增项 | 格式 | 说明 |
|---|---|---|---|
| 微信支付卡片 | 商户 API 私钥 | apiclient_key.pem | 与已有的商户证书（apiclient_cert.pem）并列；调用微信支付 APIv3 签名必需 |
| 微信公众号卡片 | 网页授权域名校验文件 | MP_verify_xxx.txt | 公众号后台生成，需放置于网页授权域名**根目录**下 |

**结论（技术确认项）**：网页授权域名校验文件属于**公众平台（公众号后台）**的要求，用于「网页授权域名 / JS 接口安全域名 / 业务域名」校验；**微信开放平台的网站应用（扫码登录）不需要校验文件**。因此上传入口放在「微信公众号」卡片，开放平台卡片不变。

### 3. 平台后台 · 机构详情 · 用量看板：商业化指标

**放置原则**：区间板块放「流量」指标（该时间段内发生的量，随时间筛选联动）；实时板块放「存量」指标（当前/累计快照，不随筛选变化）。

**区间运营分析**：原「商业化与 LLM 消耗」一张卡拆为两张：

| 卡片 | 指标 |
|---|---|
| 商业化 | 区间 GMV、净 GMV（扣退款）、付费用户、付费转化率、永享订单、退款金额、退款率 |
| LLM 消耗 | Token 消耗量、调用次数、平均响应 |

**实时订阅与资源占用**：「用户存量」卡更名「用户与营收存量」，新增「累计 GMV」。累计 GMV 是开业以来累计存量，故放实时板块而非区间板块（避免"选了近 7 天却显示累计值"的口径混乱）。0724 修订：**「内容存量」板块（KP 占用 / 已发未发下架 / 存储占用）整体删除**，不再作统计指标；实时板块保留 当前订阅卡 + 配额预警 + 用户与营收存量。

指标口径与机构后台数据看板、功能清单附表保持三方一致。

### 4. 订单状态：收敛为四态（三端同步，推翻 0716「支付成功才落库」）

#### 4.1 状态定义与微信映射

| AI 问书订单状态 | 微信 trade_state | 触发条件 |
|---|---|---|
| 待支付 | NOTPAY | 用户发起支付即落库创建订单，30 分钟支付有效期 |
| 已支付 | SUCCESS | 支付成功回调 / 查单确认 |
| 已失效 | CLOSED | 30 分钟未支付，微信自动关单（下单时传 `time_expire`） |
| 已核销 | —（无支付环节） | 兑换码订单专属 |
| 退款 / 售后 | REFUND + 退款单状态 | 独立维度，不占用订单状态位 |

要点：

- **网页支付没有「支付失败」状态**。JSAPI/H5 支付的 trade_state 只有 SUCCESS / REFUND / NOTPAY / CLOSED 四种；PAYERROR（支付失败）仅存在于线下付款码支付。用户余额不足、风控拦截等支付失败时，订单停留在 NOTPAY，可换支付方式重试——所以「待支付」态天然覆盖失败场景，无需单设失败态。
- **「已失效」微信可以返回**：下单时传 `time_expire`（当前时间 + 30 分钟），到期微信自动关单，查单得到 CLOSED；商户也可主动调关单接口。无需自建定时器判断。
- 退款走独立的退款单与退款状态（退款中 / 部分退款 / 全额退款），与订单状态解耦（沿用现有双维度设计）。

#### 4.2 三端展示

- **C 端 · 我的订单**：Tab 改为「全部 / 待支付 / 已支付 / 已失效 / 退款售后」，状态筛选 chips **单行展示不换行**。待支付订单显示剩余支付时间倒计时 + 「去支付」按钮；兑换码核销单归入「已支付」Tab，行内标签仍显示「已核销」。订单详情页的待支付倒计时条 / 已失效说明条**与基础信息面板同宽对齐**。
- **机构后台 / 平台后台 · 订单列表**：订单状态筛选为「全部 / 待支付 / 已支付 / 已核销 / 已失效」；退款状态筛选维持「全部 / 未退款 / 退款中 / 部分退款 / 全额退款」不变。
- **统计口径**：GMV、付费用户等营收指标仅计入「已支付」订单；待支付、已失效订单不计入，相关指标 tooltip 注明。

### 5. 会员指标：新增 / 续费 / 回流 三分

| 指标 | 口径 | 位置 |
|---|---|---|
| 新增会员 | 区间内**历史首次**开通会员的用户数（续费、回流均不计入） | 两后台（口径修订） |
| 续费率 | 区间内到期且完成续费的会员数 ÷ 同区间到期会员数 | 机构后台已有；**平台后台本批新增** |
| 回流会员 | 区间内开通会员、且开通时会员状态为已过期的用户数（不算新增、不算续费） | **两后台本批新增** |

三者互斥：任一次开通行为只落入其中一类。

### 6. 指标去重规则（全量落 tooltip）

统一原则：

- **规模指标按用户去重**：区间内按用户 ID 精确去重，同一用户多天活跃只算 1 人。适用：活跃用户、新增 C 端、付费用户、提问用户等。
- **强度指标按人天**：用户 × 自然日。适用：日均活跃（DAU 均值）、人均提问等。

例：张三在 7 天区间内第 1、2 天活跃、第 3 天起未来——「活跃用户」计 **1**，「日均活跃」贡献 **2 个人天**。

**展示规范（0724 定稿）**：

1. 两后台所有涉及去重的指标，tooltip 面板内去重规则**独立成一条无序项**，格式统一为「· 去重：xxxx」，不再混在定义句里；
2. 功能清单的「数据看板指标」「用量看板指标」两张表**单独增加「去重规则」列**，逐指标标注。

### 6.1 数据看板：活跃概览与留存修订（0724）

**日活 / 周活 / 月活改为固定滚动窗口快照，不随区间筛选联动。**

原因（第一性原理）：区间筛选回答"这段时间表现如何"，而 WAU/MAU 的定义本身就带固定窗口（近 7 / 30 日），两者绑定会产生无法自洽的语义——选「近 7 天」时 WAU 恰好等于区间去重活跃（重复指标）；选「30 天」或自定义 90 天时，"对应的 7 日窗口"取哪一段没有唯一答案。因此定稿：

| 指标 | 口径 | 环比 |
|---|---|---|
| 日活 DAU | 今日 00:00 至当前时刻的去重活跃（实时） | 对比昨日同时段 |
| 周活 WAU | 截至今日的近 7 日滚动窗口去重活跃 | 对比上一个 7 日窗口 |
| 月活 MAU | 截至今日的近 30 日滚动窗口去重活跃 | 对比上一个 30 日窗口 |

**位置**：既然三卡不随区间联动，就整体挪出「区间分析」——置于页面顶部、「用户留存」上方，与留存同为页级常驻区块（快照/留存两个非区间口径连在一起），区块标题「活跃概览 · 实时滚动窗口快照 · 不随下方时间筛选联动」；「区间分析 · 用户分析」Tab 内不再有活跃概览。区间维度的活跃规模看「活跃用户（区间去重）」。

**用户留存注册批次精简**：批次选项只保留「最新可统计」与「自定义日期」，删除「近 7 个注册日 / 近 30 个注册日」两档。

### 7. C 端 · 语音验证码兜底（新增交互）

覆盖 C 端全部短信验证码场景（登录、绑定手机号）：

1. 发送短信验证码后进入 60 秒倒计时。
2. 倒计时结束仍未输入 → 输入框下方出现次级入口：**「未收到短信验证码？接听语音电话获取」**。
3. 点击即拨打（不加确认弹窗，点击即同意），入口原地变为状态行：**「语音电话拨打中 · 来电以 95013 开头，请留意接听」**——号码开头提示在点击瞬间原地出现，并在等待期间常驻，避免用户当骚扰电话拒接。
4. 拨打中状态行常驻「N 秒后可重拨」倒计时；归零后变为「未接到电话？**再次拨打**」，点击立即重拨（有 toast 反馈）并重启 60 秒，可循环重拨。
5. **语音码与短信码同码同校验**：提交时真实校验（原型演示码 123456，输入框下方常驻提示），输错 toast「验证码错误，请重新输入」并拦截，输对才放行——登录 / 绑定 / 换绑三处一致。
6. 倒计时实现要求（0724 修订）：按**截止时间戳**计算剩余秒数，不能逐秒递减——浏览器对后台标签页 / 锁屏会节流定时器，用户切去微信等验证码再切回时逐秒递减会变慢数倍，语音入口迟迟不出现；监听 visibilitychange 切回即校准（短信重发、语音重拨、订单待支付倒计时同规则）。
7. **频控要求（后端实现，原型不做交互）**：语音重拨需设次数上限——建议同一手机号**单次验证流程连续重拨 ≤ 3 次、每日 ≤ 5 次**，超限返回明确错误码，前端按返回提示「拨打次数已达上限，请稍后再试或联系客服」；短信发送同样按供应商频控（通常 1 条/分钟、每日上限）做服务端限流。目的：防骚扰投诉（外呼号码被标记会拖垮整体接通率）、防刷接口费用。
8. ⚠️ 「95013」为原型演示号段，实际外呼号段以短信/语音供应商分配为准，上线前替换文案。

## 二、已确定的业务与技术结论

### 1. 微信支付：两个产品、一套订单模型

| 场景 | 微信产品 | 下单 API | 依赖 |
|---|---|---|---|
| 微信内浏览器 | JSAPI 支付 | /v3/pay/transactions/jsapi | 已认证服务号 + 网页授权拿 openid |
| 外部浏览器（Chrome/百度等） | H5 支付 | /v3/pay/transactions/h5 | 单独申请 H5 支付权限 |

- 两个产品**分别申请开通**，但查单 / 关单 / 退款接口共用，订单状态模型一致（见一-4.1），后端订单逻辑一次成型。
- 产品介绍：[JSAPI 支付](https://pay.weixin.qq.com/doc/v3/merchant/4012062524)、[H5 支付申请指引](https://pay.weixin.qq.com/doc/v3/merchant/4012791841)。

### 2. H5 支付申请时序与审核要求

- **不要求全部开发完成**。审核要求填写的网站域名下有**可访问的页面**、能体现真实业务场景（与经营类目一致的商品/价格/订单流程/支付按钮）。H5 支付权限开通前技术上无法调起真实支付，审核本来就只能人工浏览页面——支付按钮点击后给「支付暂未开通」提示即可。常见驳回原因是页面空壳（「无实际业务场景」），内容需做实（真实书目、真实价格）；驳回后可完善重提。
- **域名与商户号主体**：要求 ICP 备案主体与商户号主体一致；不一致需上传 **ICP 备案授权书**（域名备案主体盖章）+ 双方合作证明（合同/协议；集团关系提供公网可查关系证明 + ICP 主体营业执照）。**建议支付域名备案主体直接与商户号主体保持一致**，免去授权材料与审核风险。
- **建议时序**：① 先申请开通 JSAPI 支付（依赖认证服务号，门槛低）并开发微信内支付；② 同期在正式域名部署简易业务页，提交 H5 支付申请；③ H5 审核通过（7 个工作日内）后开发外部浏览器支付。

### 3. 自动续费：委托代扣（扣费服务 · 预约扣费）

- **流程**：用户签约（授权关系）→ 每期扣款日前一天商户调「预约扣费」接口 → 微信 30 分钟内向用户发预扣费通知 → 商户调「受理扣款」完成扣款。参考：[扣费服务产品介绍](https://pay.weixin.qq.com/doc/v3/merchant/4012161105)、[预约扣费](https://pay.weixin.qq.com/doc/v3/merchant/4012467036)。
- **扣款日后移不影响签约**：微信侧没有固定扣款日，每期扣款时点由商户发起预约决定。权益顺延导致扣款日推迟，只是商户侧调度晚一期发起预约，签约协议不动，不存在「到期扣不出」问题。
- **系统需记录**：「下次扣款日」字段 + 变更历史（变更原因：兑换码顺延 / 退款收回 / 手动调整，关联来源单据）。
- **签约模板金额**：模板扣费金额类型分「为」（固定）与「不高于」（上限）。机构后台可调价 → **申请「不高于」型模板**，上限覆盖机构可调价区间；用固定金额模板会因实际扣款与模板不符导致扣款失败/模板失效——这是申请时的关键决策。
- 代扣为受限能力，需在商户平台提交场景申请（含业务介绍、扣费周期、金额、会员服务内容）。

### 4. 会员权益：分段记账原则（含兑换码冲突处理）

统一原则：**每段会员时长记账**，记录 `{来源类型（购买/兑换码/赠送）, 来源单据, 起止时间, 状态}`；同类权益按时间**顺延排队**；退款**按来源段收回**。

冲突矩阵：

| 场景 | 处理 |
|---|---|
| 已是会员（购买）再兑换兑换码 | 兑换段接在当前到期日之后顺延生效 |
| 开通自动续费 + 兑换兑换码 | 兑换段顺延；下次扣款日推迟至全部权益段耗尽前（商户侧调度，见二-3，需记录变更） |
| 购买单全额退款、队列中还有兑换段 | 只收回该购买单对应的时间段；兑换段自动前移，自退款生效日起顶上 |
| 购买单部分退款 | 权益不收回（沿用现行规则） |
| 多张兑换码连续兑换 | 依次顺延排队 |
| 会员 × 永享 | 两池独立互不影响（既定规则）：会员是全库时限权益，永享是单 KP 永久权益 |
| 收回的段正在生效 | 会员立即降级到队列中下一段；无下一段则会员失效 |
| 收回的段尚未开始 | 直接从队列移除，后续段前移 |

### 5. 短信到达率问题与缓解方案

**问题本质**：短信链路为 供应商 → 三大运营商**各省网关** → 手机。各省各运营商对短信签名/码号要求实名报备，进度参差，且部分运营商不向供应商回传结果——未报备通的地区会**静默丢弃**短信，供应商与商户均看不到真实失败。因此出现「需该地区用户先反馈收不到，供应商才去疏通该地区」的现象。这是行业通病（阿里云/腾讯云/华为云机制相同），换供应商不能根治。

**缓解组合（后端/运营侧，原型不涉及）**：

1. **事前**：签名/资质在各运营商报备做全，控制台核对报备状态；
2. **事中**：监控发送回执，某地区/运营商失败率异常时主动提工单要求疏通，不等用户投诉；
3. **兜底**：验证码等关键短信失败后自动切换备用通道——第二家供应商双通道灾备 + 语音验证码兜底（行业标配）；
4. **内容**：避开营销敏感词，降低网关拦截概率。

**语音为什么不受地区不达影响**：短信走「行业短信通道」（106 端口号），必须过省级短信网关的报备/拦截体系；语音验证码本质是一通电话，走语音通话网，不经过短信网关——只要号码有效、手机开机即可呼达。语音自身的失败模式是用户不接陌生来电/号码被标记骚扰，因此定位为**短信失败后的兜底**（产品化交互见一-7），不是全量替代。
